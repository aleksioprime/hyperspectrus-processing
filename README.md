# hyperspectrus-processing

Разработка пакетов с алгоритмами обработки для HyperSpectRus: контракт, шаблон пакета и приёмочные проверки

Алгоритм восстановления концентраций хромофоров подключается к рабочему месту врача отдельным пакетом, без единой правки в приложении. Здесь лежит всё, что нужно, чтобы такой пакет написать: описание контракта, готовая заготовка, набор приёмочных проверок и тестовые данные. Пакет, прошедший проверки, встраивается в рабочее место и выходит к клиникам с очередной версией программы.

## С чего начать

```bash
git clone https://github.com/aleksioprime/hyperspectrus-processing
cd hyperspectrus-processing
uv sync --all-packages
cp -r template/hsr-proc-myalgo ../hsr-proc-<ваше-имя>
```

Дальше три шага, каждый проверяется командой:

| Шаг | Команда | Что должно получиться |
|---|---|---|
| Пакет виден рабочему месту | `uv run python -m hsr_proc` | реализация есть в списке |
| Расчёт написан | `uv run hsr-proc-check` | вердикт «ПРИНЯТ» |
| Результат выглядит осмысленно | `uv run hsr-proc-run --synthetic --out out` | карты и `metrics.json` в каталоге `out` |

Заготовка возвращает пустые карты правильного вида: проверки уровня `contract` на ней проходят сразу, числовые падают - так и должно быть, пока расчёт не написан. Ищите пометки `ЗДЕСЬ` в `src/hsr_proc_myalgo/processor.py`.

Контракт целиком - [CONTRACT.md](CONTRACT.md). Его стоит прочитать до того, как писать расчёт: половина замечаний на приёмке про то, что в нём уже написано.

## Проверки

Набор разделён на три уровня, и разница между ними существенна.

**`contract`** - обязательное. Реализация, не прошедшая этот уровень, сломает рабочее место или молча испортит результат: перепутает концентрации, оставит NaN в карточке сеанса, полезет в сеть со снимками пациента. Такой пакет не принимается.

**`numeric`** - числа. Проверяется по синтетическим наборам, где правильный ответ известен заранее: по заданным концентрациям строятся яркости, и алгоритм обязан вернуть исходные концентрации. Наборы построены на линейной модели. Если ваш алгоритм построен на другой, часть сверок отключается объявленным отступлением - см. раздел «Другая модель» в [CONTRACT.md](CONTRACT.md#другая-модель).

**`budget`** - время обработки кадра прибора. Не приговор, но число в отчёте: врач ждёт результат у экрана.

```bash
uv run hsr-proc-check                      # все уровни, вердикт в консоль
uv run hsr-proc-check --level contract     # только обязательное
uv run hsr-proc-check --report приёмка.md  # отчёт для передачи
uv run pytest -m contract                  # то же из своих тестов
```

Набор проверяет сам себя: в `tests/` лежит заведомо правильная реализация, на которой обязаны проходить все уровни, и подопытные с одним внесённым нарушением каждый, на которых обязана падать ровно одна проверка. Проверка, которая ничего не ловит, хуже отсутствующей.

## Передача пакета

1. Зелёные проверки в вашем CI. Красные разбираются до отправки: у принимающего они будут теми же.
2. Тег и релиз с колесом `.whl`, отчётом `hsr-proc-check --report` и строкой в вашем CHANGELOG.
3. Имя реализации (`name`) между версиями не меняется: по нему отличают, каким алгоритмом посчитан сеанс. Версия поднимается при **любом** изменении расчёта, включая смену допусков.

Дальше пакет ставится в окружение сборки рабочего места, проходит те же проверки на стороне издателя и попадает в очередную полную версию программы. Отдельным файлом врачу алгоритм не передают: рабочее место поставляется одним исполняемым файлом, доустановить в него пакет некуда.

## Вопросы и изменения контракта

Вопросы - в Issues этого репозитория. Контракт развивается; что изменилось и что от этого ломается - в [CHANGELOG.md](CHANGELOG.md). Группа точек входа `hsr_proc.processors` не меняется никогда: иначе разом отвалятся все написанные пакеты.
