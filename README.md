# hyperspectrus-processing

Репозиторий для разработки алгоритма обработки HyperSpectRus

**Разработчик алгоритма** пишет расчёт, проверяет его и доводит до версии, готовой к передаче. **Разработчик приложения** принимает эту версию, переносит её в `hyperspectrus` и выпускает с ней рабочее место врача.

## Структура

Каталоги разделены по тому, уезжает содержимое в приложение или остаётся здесь:

|  | Уезжает в приложение | Остаётся здесь |
|---|---|---|
| **Код** | `packages/hsr-proc-base` и `packages/hsr-proc-algo` - ложатся туда зеркалом | Остальные пакеты расчётов, `conformance`, `tools`, `tests` |
| **Данные** | `references` - справочник, копируется точь-в-точь | `datasets` - учебные кадры, `real` в Git не попадает |

| Каталог | Назначение |
|---|---|
| [`packages/hsr-proc-algo`](packages/hsr-proc-algo) | Расчёт, который уезжает в приложение. С него начинают, в него же переносят победивший вариант |
| [`packages/hsr-proc-base`](packages/hsr-proc-base) | Контракт: структуры входа и результата, реестр реализаций |
| `packages/hsr-proc-<имя>` | Другие расчёты для сравнения. Создаются `tools/new_algo.py`, живут только здесь |
| [`conformance`](conformance) | Приёмочные проверки и команды разработки; в рабочее приложение не входят |
| [`references`](references) | Справочник спектров и матрица перекрытий |
| [`datasets`](datasets) | Учебные серии и правила для тестовых данных |
| [`tools`](tools) | Создание пакетов и передача в приложение |

## РАЗРАБОТЧИКУ АЛГОРИТМА

### Начало работы

```bash
git clone https://github.com/aleksioprime/hyperspectrus-processing
cd hyperspectrus-processing
uv sync
```

`uv sync` собирает окружение: ставит зависимости и подключает местные пакеты исходниками. Правки в `.py` после этого действуют сразу. Повторять команду нужно только после правки `pyproject.toml` - добавили зависимость, тронули точку входа, подняли версию пакета. Она же чинит окружение, если что-то перестало импортироваться.

Расчёт живёт в [`packages/hsr-proc-algo`](packages/hsr-proc-algo). Сейчас там тот самый алгоритм, который работает в рабочем месте врача: оптическая плотность, решение системы по матрице коэффициентов, карта THb, выделение очага порогом Отсу и коэффициент s. Он проходит приёмку целиком, и это отправная точка исследования: любое изменение сразу видно на фоне рабочего поведения. Переписывать всё сразу не нужно - можно заменить сегментацию, оставив восстановление концентраций, и наоборот.

Рядом заводят сколько угодно других расчётов и сравнивают их между собой, см. [Второй расчёт рядом](#второй-расчёт-рядом). В приложение уезжает один - `hsr-proc-algo`.

### Команды

Все команды запускаются из корня репозитория. `uv run` сам поднимает окружение, отдельно активировать `.venv` не нужно.

| Команда | Что делает | Когда запускать |
|---|---|---|
| `uv sync` | Собирает окружение: зависимости и местные пакеты исходниками | После клонирования и после каждой правки `pyproject.toml` |
| `uv run pytest` | Гоняет все тесты репозитория | На каждую правку расчёта |
| `uv run hsr-proc-check hsr-proc-algo` | Приёмка: 24 проверки и вердикт | Перед передачей и после заметных правок |
| `uv run hsr-proc-run datasets/example/jpeg/1 --out out/1` | Кладёт в каталог карты и `metrics.json` | Когда нужно посмотреть на результат глазами |
| `uv run python -m hsr_proc` | Показывает реализации, которые видит рабочее место | Если расчёта «не видно» |
| `uv run python tools/new_algo.py <имя>` | Создаёт пакет ещё одного расчёта | Когда нужен второй вариант для сравнения |
| `uv run python tools/promote_algo.py <имя> --version X.Y` | Делает этот расчёт основным | Когда он выиграл и заменяет `algo` |

### Контракт обработки

Прибор снимает один участок кожи в нескольких спектрах: геометрия кадра одна, длины волн разные. Рабочее место передаёт спектральный куб и матрицу коэффициентов поглощения хромофоров.

Алгоритм должен восстановить карты концентраций, вычислить карту общей концентрации гемоглобина (THb), выделить область поражения и вернуть средние THb в поражении и коже вместе с их отношением. Сохранением файлов, базой данных и интерфейсом занимается рабочее место.

От реализации нужны три вещи: имя, версия и сам расчёт. В коде это два поля и один метод:

```python
class AlgoProcessor:
    name = "algo"
    version = "1.0"

    def process(self, request, progress=None):
        ...
        return ProcessingResult(...)
```

| | Что это | Зачем |
|---|---|---|
| `name` | Имя реализации | По нему рабочее место выбирает расчёт |
| `version` | Версия расчёта | Попадает в карточку сеанса, по ней сравнивают выпуски |
| `process` | Сам расчёт | Принимает `ProcessingRequest`, возвращает `ProcessingResult`; второй аргумент - необязательный обратный вызов хода работы |

Это протокол `hsr_proc.Processor`. Наследоваться от специального класса не нужно: проверяется, что эти три вещи на месте, а не происхождение класса.

У пакета, который уезжает в приложение, имя пакета, модуль, точка входа и `name = "algo"` согласованы с рабочим местом и не меняются - по этому имени оно выбирает расчёт. Всё остальное правится свободно. `version` поднимается при любом изменении расчёта.

#### Вход

`ProcessingRequest` содержит:

| Поле | Содержание |
|---|---|
| `cube` | `SpectralCube`: массив `(спектры, высота, ширина)` типа `float32`, значения от 0 до 1 и длины волн в порядке кадров |
| `overlap` | `OverlapMatrix`: строки соответствуют длинам волн, столбцы - хромофорам |
| `params` | `ProcessingParams`: общий `gaussian_sigma` и словарь `extra` для параметров алгоритма |

Порядок строк матрицы может отличаться от порядка слоёв куба. Перед расчётом обязательно вызывайте:

```python
matrix = request.overlap.aligned_to(request.cube)
```

Метод одновременно переставляет строки и проверяет наличие коэффициентов для всех снятых длин волн.

#### Выход

Нужно вернуть `ProcessingResult` со всеми полями:

| Поле | Содержание |
|---|---|
| `concentrations` | Карта `float32` размером с кадр для каждого хромофора справочника |
| `thb_map` | Карта общей концентрации гемоглобина `float32` |
| `lesion_mask` | Маска поражения типа `bool` |
| `metrics` | Коэффициент s и средние THb в поражении и коже |
| `segmentation` | Метод сегментации, порог и использованное сглаживание |
| `processor` | Ровно `f"{self.name} {self.version}"` |
| `notes` | Допущения и предупреждения для врача |

Размер всех карт совпадает с размером кадра. NaN и бесконечные значения не допускаются.

#### Точка входа

Рабочее место находит алгоритм по точке входа, а не прямым импортом:

```toml
[project.entry-points."hsr_proc.processors"]
algo = "hsr_proc_algo:AlgoProcessor"
```

Без этой записи реализация не появится в рабочем месте, причём молча: её просто не будет в списке. В пакете точка входа уже настроена. Читается она из метаданных установленного пакета, поэтому после правки нужен `uv sync`.

Состав входа и результата тоже можно менять - это тот же репозиторий, - но такое изменение затрагивает обе стороны, поэтому согласуется отдельно и поднимает версию пакета `hsr-proc-base`. Расчёт меняют свободно, контракт - по договорённости.

### Проверки

Набор [`hsr-proc-conformance`](conformance) нужен только при разработке и приёмке, в рабочее приложение он не входит. Одни и те же проверки запускают обе стороны, поэтому разойтись в выводах они не могут.

| Уровень | Что проверяет |
|---|---|
| `contract` | Форму результата, типы, отсутствие NaN, неизменность входа, отсутствие файлового и сетевого ввода-вывода |
| `numeric` | Концентрации, THb, сегментацию и показатели на синтетических данных с известным ответом |
| `budget` | Время обработки кадра прибора |

```bash
# Самый быстрый ответ на вопрос «я ничего не сломал?»: обязательный уровень.
uv run pytest -m contract packages/hsr-proc-algo

# Приёмка с отчётом в файл: его прикладывают к передаче расчёта.
uv run hsr-proc-check hsr-proc-algo --report приёмка.md
```

### Если числовые проверки падают, а расчёт верен

Уровень `numeric` сверяет результат с синтетическими наборами, построенными на линейной модели: оптическая плотность складывается из концентраций по матрице коэффициентов. Расчёт, который учитывает рассеяние или опирается на обученную модель, эту модель точно не воспроизводит - и провалит сверку концентраций, будучи при этом лучше.

На такой случай допуски ослабляются, но вместе с причиной, в [`conformance.toml`](packages/hsr-proc-algo/src/hsr_proc_algo/conformance.toml) внутри пакета:

```toml
profile = "custom"
concentration_atol = 1e-3
deviations = [
    "Модель учитывает рассеяние, точное обращение линейной системы не воспроизводится",
]
```

Причина обязательна: без непустого `deviations` проверка `test_послабления_объяснены` пакет не пропустит. Она же печатается в отчёте приёмки отдельным разделом - принимающий видит, чем расчёт расходится с эталонной моделью, и решает, приемлемо ли это. Уровень `contract`, выделение очага и коэффициент s обязательны при любом профиле.

Файл лежит внутри пакета, потому что уезжает вместе с ним: `pyproject.toml` в передачу не попадает, и настройки из него на приёмке не прочитались бы.

### Второй расчёт рядом

Сравнивать два расчёта удобнее, когда подключены оба: команды умеют выбирать между ними по имени. Пакет создаётся одной командой:

```bash
# Копия действующего расчёта - когда меняют его часть и сравнивают с прежним.
uv run python tools/new_algo.py newalgo

# Пустой расчёт с пометками ЗДЕСЬ - когда пишут с нуля.
uv run python tools/new_algo.py newalgo --blank
```

Команда делает `packages/hsr-proc-newalgo`: переименовывает модуль, класс, точку входа и имя реализации, разводит имена файлов тестов (два `test_processor.py` в разных пакетах pytest не соберёт) и дописывает две строки в корневой `pyproject.toml`. Отдельной папки с образцом в репозитории нет намеренно: она отстала бы от контракта молча, а заготовка делается из пакета, который сегодня проходит приёмку.

После `uv sync` подключены оба расчёта:

```bash
uv run python -m hsr_proc                       # оба в списке, выбор не сделан
uv run hsr-proc-check hsr-proc-newalgo          # приёмка второго
uv run hsr-proc-run --synthetic --processor newalgo --out out/new
```

Пока расчёт не написан, числовые проверки на нём падают - это нормально, и `uv run pytest packages/hsr-proc-newalgo -m contract` проверяет только то, что уже должно работать.

Второй пакет живёт только здесь: в приложение уезжает `hsr-proc-algo`.

### Когда новый расчёт победил

Основным становится он, но уезжает в приложение по-прежнему `hsr-proc-algo` - имя `algo` записано в настройках рабочего места, и менять его в одиночку нельзя. Замена делается командой:

```bash
uv run python tools/promote_algo.py newalgo --version 1.1
```

Она переносит в `hsr-proc-algo` расчёт, тесты, зависимости и допуски приёмки, возвращает имя класса и реализации, ставит новую версию и убирает пакет-источник. Версию называете вы: она попадает в карточку сеанса, поэтому только растёт - команда откажется, если названная не больше нынешней.

Работает команда на чистом дереве: она перезаписывает и удаляет файлы, и без зафиксированного состояния замену не разглядеть в diff и не откатить. Дальше обычная проверка:

```bash
uv sync
uv run hsr-proc-check hsr-proc-algo --report приёмка.md
uv run pytest
```

### Тестовые данные

Синтетические серии создаются автоматически. Сгенерированный файловый пример лежит в `datasets/example/` - три наблюдения, где пятно от первого к третьему бледнеет:

```bash
uv run hsr-proc-run datasets/example/jpeg/1 --out out/1
```

Справочник коэффициентов команда берёт из `references` сама, указывать его нужно только если он лежит не там.

Настоящие кадры кладутся в `datasets/real/jpeg/` по правилам из [`datasets/README.md`](datasets/README.md) и не фиксируются в Git. Снимки пациентов не должны попадать в этот репозиторий.

Рабочая конфигурация `HSR-EXAMPLE` хранится в [`references/hsr-example.json`](references/hsr-example.json). В отличие от контракта, здесь главным является этот репозиторий: разработчики алгоритма подбирают коэффициенты, меняют `reference_version` и проверяют расчёт на них. В приложение уходит точная копия файла, и переносит её, как и всё остальное, принимающая сторона.

### Перед передачей

1. Поднимите `AlgoProcessor.version` при любом изменении расчёта. Версия попадает в карточку сеанса и только растёт: в приложении сейчас работает `algo 1.0`.
2. Добейтесь успешного `uv run hsr-proc-check hsr-proc-algo --report приёмка.md`.
3. Поставьте тег версии, например `algo-v1.1`, и отправьте его вместе с отчётом.

На этом работа над версией закончена: дальше её забирает разработчик приложения.

## РАЗРАБОТЧИКУ ПРИЛОЖЕНИЯ

Расчёт разрабатывают здесь, а работает он в `hyperspectrus`. Три вещи приезжают оттуда сюда, и все три - копиями с контрольными суммами:

| Что | Откуда | Когда обновляется |
|---|---|---|
| Пакет расчёта `hsr-proc-algo` | `packages/hsr-proc-algo` | Под выпуск рабочего места |
| Контракт `hsr-proc-base` | `packages/hsr-proc-base` | Только по согласованному изменению состава входа или результата |
| Справочник спектров | `references/hsr-example.json` | После изменения коэффициентов перекрытия |

Рядом с копией пакета ложится `MIRROR.json` - коммит источника и суммы файлов. Тест приложения сверяет их и не даёт править копию на месте: правка разошлась бы с тем, что осталось у разработчика алгоритма, и пропала бы при следующей передаче. Нужна правка - она вносится здесь и передаётся заново.

### Приём версии расчёта

```bash
make accept-algo VERSION=algo-v1.1
```

Команда запускается **в репозитории приложения**. Она забирает названную версию из соседнего репозитория разработки (`ALGO_PATH`, если он лежит не рядом), переносит пакет, ставит его и повторяет приёмку - тем же набором, каким её прогоняли здесь. Версия берётся отдельным рабочим деревом по тегу, поэтому чужой рабочий каталог не трогается, а в `MIRROR.json` не может попасть незафиксированное состояние.

Дальше остаётся `make check` и коммит: зеркало обязано быть в репозитории, иначе сборка в Actions его не увидит. Собранная версия рабочего места несёт расчёт внутри себя; отдельно доустановить его в поставленное врачу приложение нельзя.

Колесом передавать нельзя, хотя `uv build --package hsr-proc-algo` и соберёт его: в приложении пакет с тем же именем подключён членом workspace, и ближайший `uv sync` вернул бы прежний расчёт - молча, вместе с собранной версией программы.

### Контракт и справочник

Эти две вещи переносятся вручную и редко:

```bash
uv run python tools/sync_contract.py     # после согласованного изменения контракта
uv run python tools/sync_reference.py    # после изменения коэффициентов
```

Команды запускаются из корня **этого** репозитория и требуют, чтобы оба репозитория были под рукой. Зеркало контракта обновляется целиком: приложение либо переходит на новую версию, либо остаётся на предыдущей согласованной.

### Команды

| Команда | Что делает | Когда запускать |
|---|---|---|
| `make accept-algo VERSION=algo-v1.1` | Забирает версию расчёта, переносит её и прогоняет приёмку. Запускается **в репозитории приложения** | Когда готовится выпуск рабочего места |
| `uv run python tools/sync_algo.py` | Переносит расчёт вручную, без приёмки и проверок | Если удобнее отсюда и оба репозитория под рукой |
| `uv run python tools/sync_contract.py` | Переносит контракт | После согласованного изменения состава входа или результата |
| `uv run python tools/sync_reference.py` | Переносит справочник коэффициентов | После изменения коэффициентов перекрытия |
